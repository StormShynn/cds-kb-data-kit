# cds-kb-data

Private **data + automation** repository for the SAP CDS Knowledge Base — consumed
read-only by the [`cds-kb-mcp-kit`](https://github.com/StormShynn/cds-kb-mcp-kit) MCP
server, via a local clone or the authenticated GitHub Contents API.

This repo owns the whole fetch/tag/enrich pipeline. `cds-kb-mcp-kit` only serves
what's already here — it has no fetch/scraping code of its own.

## Contents

```
views/<MODULE>/.../            CDS view definitions, one .md each (YAML frontmatter +
                               fields + associations + DDL source when available),
                               nested one folder per app_component segment, each
                               named by its cumulative prefix (MM-IM-GF -> MM/MM-IM/
                               MM-IM-GF/) — MISC/ for the few with no component,
                               _UNVERIFIED/ for release_state: unverified regardless
                               of module, so items needing review aren't scattered
index/search_index.json       Pre-built MiniSearch (BM25) search index (self-describing)
index/view-paths.json         NAME -> real path (e.g. "views/FI/I_X.md") — lets views
                               live in any folder layout without cds-kb-mcp-kit needing
                               to know the scheme; consulted before falling back to a
                               flat views/<NAME>.md guess
index/taxonomy.json           LoB -> Business Object -> keyword map, used for tagging
index/version.json            {commit, builtAt, viewCount, enrichedCount} — lets
                               consumers skip re-downloading the index when unchanged
changelog.json                Append-only log of every add/update/skip/error
coverage.json / coverage-report.html   Diff against the SAP Business Accelerator Hub's
                               released-view catalog (missing / metadata-only / full)
dashboard.html                 Activity dashboard rendered from changelog.json
overview.html                  Tabbed shell embedding dashboard.html + coverage-report.html
                               via iframes — open this one for both at once. Static,
                               not regenerated by any script (nothing about it depends
                               on the data, only on the other two files existing)
hub-metadata-manifest.json     Tracks which views scripts/add_hub_metadata.mjs wrote,
                               so it never overwrites a real DDL-sourced entry
```

Since this repo is private with no Pages deploy, none of these `.html` files
render on github.com — pull the repo and open `overview.html` locally (or in
VS Code's Live Preview) instead.

## Automation scripts

| Script | Purpose |
|---|---|
| `add_view.mjs` | Add one view (from a DDL file/inline text, or `--source github`) |
| `batch_add.mjs` | Add many views at once (`--source github`, `--dir`, `--list`) |
| `enrich_index.mjs` | Rebuild `index/search_index.json` and `index/view-paths.json` from the current `views/` |
| `scripts/check-coverage.mjs` | Diff against the Hub's released-view catalog |
| `scripts/add_hub_metadata.mjs` | Fill in Hub-confirmed views missing locally (metadata-only) |
| `scripts/backfill_source_links.mjs` | Best-effort re-link pre-existing DDL entries with no recorded source |
| `scripts/generate-dashboard.mjs` | Render `dashboard.html` from `changelog.json` |
| `scripts/migrate-to-module-folders.mjs` | Reconcile every view's folder against its current `app_component`/`release_state` — safe to re-run any time, no-op when nothing's misplaced |

Zero npm dependencies except `minisearch` (used only by `enrich_index.mjs`).

### Optional: SAP API key

`check-coverage.mjs` and `add_hub_metadata.mjs` call the SAP Business
Accelerator Hub's public catalog, which works with zero authentication today
(confirmed by every run of these scripts). Setting a `SAP_API_HUB_KEY` env
var (or a `SAP_API_HUB_KEY` repo secret, for the `check-coverage.yml` /
`hub-metadata-fetch.yml` workflows) adds it as an `APIKey` header on those
calls — a fallback in case the Hub ever tightens anonymous access, not
something currently required. Same header convention as
[`mcp-sap-docs`](https://github.com/StormShynn/mcp-sap-docs)'s
`SAP_API_HUB_KEY`. Get a key by registering on
[api.sap.com](https://api.sap.com) and subscribing to an app.

## Automation (GitHub Actions)

| Workflow | Schedule | What it does |
|---|---|---|
| `daily-fetch.yml` | daily 06:00 UTC | Searches GitHub for new CDS views, opens a PR (`release_state: unverified`, needs review) |
| `hub-metadata-fetch.yml` | daily 07:00 UTC | Fills in Hub-confirmed-released views missing locally, opens/updates one rolling PR |
| `check-coverage.yml` | every 6h + on push to `views/**` | Regenerates `coverage.json`/`coverage-report.html`, pushes directly |
| `update-dashboard.yml` | on push to `changelog.json`/`views/**` | Regenerates `dashboard.html`, pushes directly |
| `resync-folders.yml` | on push to `views/**` | Runs `npm run resync-folders` (see below), pushes any resulting moves directly |

This repo is private — there is intentionally no GitHub Pages deployment here.

### Fixing a wrong `app_component` by hand

Edit the `app_component:` line in the view's `.md` file (wherever it currently
sits) and either:

- **Push it** — `resync-folders.yml` picks up the change automatically and
  moves the file if it no longer matches its folder (usually within a minute
  or two of the push finishing).
- **Or run it yourself first**, if you want to see the move locally before
  pushing: `npm run resync-folders`. Safe to run any time — it only touches
  files that are actually in the wrong place, and also refreshes
  `index/view-paths.json` so `get_cds_view` finds the view at its new path
  immediately, without waiting on cds-kb-mcp-kit's periodic index refresh.

## Where `app_component` comes from

This field drives both `tags`/module filtering and which nested `views/<MODULE>/.../`
folder a view lands in (see `resolveViewFolder` in `scripts/lib/view-files.mjs`),
so it's worth being precise about where it's actually set — it is **not**
parsed out of the DDL source itself (ABAP CDS views don't carry an annotation
for it, and `src/parser.mjs`'s `parseDDL()` never extracts one, despite its
header comment listing `appComponent` in the return shape).

Three real sources, in the order a view is likely to hit them:

1. **Hub catalog fetch** — `add_hub_metadata.mjs`, via `fetchFromHubCatalog()`
   in `src/fetcher.mjs`. Reads `application_component` straight from SAP's own
   public catalog API response. The only fully-automatic, SAP-confirmed source.
2. **Explicit `--app-component <code>` flag** — `add_view.mjs` / `batch_add.mjs`.
3. **3rd column of a `--list` file** (`ViewName | ddlPath | app_component | description`).

The daily GitHub-search discovery pipeline (`daily-fetch.yml` →
`batch_add.mjs --source github`) supplies **none** of these — `listFromGitHub()`
and `fetchFromGitHub()` in `src/fetcher.mjs` never return an app component,
and the workflow never passes `--app-component`. A view that only ever went
through that path keeps an empty `app_component` unless someone fills it in
by hand later — which is exactly why `views/MISC/` and `views/_UNVERIFIED/`
exist (see "Contents" above).

## How cds-kb-mcp-kit connects to this repo

The server reads exactly three kinds of paths at runtime:

| Path | Purpose |
|---|---|
| `index/search_index.json` | Full-text search index (loaded once at startup, refreshed periodically) |
| `index/view-paths.json` | NAME -> real path, checked before guessing `views/<NAME>.md` |
| `views/<MODULE>/.../<NAME>.md` | Individual view definitions (loaded on demand) |

Locally via `--data <clone>`, or remotely via `--remote https://raw.githubusercontent.com/StormShynn/cds-kb-data/main`
plus a token (`CDS_KB_DATA_TOKEN` or `GITHUB_TOKEN`) with read access to this repo —
see `cds-kb-mcp-kit`'s `src/datasource.mjs`.

**Wiring up a different consumer?** See [CONNECTING.md](./CONNECTING.md) —
access setup, the same data contract in more detail, and what to do if
you're not on Node.js/MiniSearch.
